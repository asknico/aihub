# DDD Rules

> 适用范围：领域建模与领域层的设计约束。
> 边界：分层结构与依赖方向见 `clean-architecture.md` / `hexagonal.md` /
> `dependency-rules.md`；服务拆分见 `microservices.md`；模块边界见
> `modular-monolith.md`。本文件聚焦**领域模型本身**。
> 相关：编码层规则见 `coding/java/java.md`，聚合落地见 `coding/spring/spring-boot.md`。

## 0. 核心原则

1. **领域模型是资产，不是数据容器**：模型承载业务规则，不只是表结构映射。
2. **不变量由模型保证**：任何绕过模型的修改都是缺陷入口。
3. **边界先于细节**：先划限界上下文，再谈类怎么设计。
4. **语言统一**：代码中的术语必须与业务方使用的术语一致。
5. **依赖倒置**：领域定义接口，基础设施实现接口。

## 1. 战略设计（Strategic design）

- **限界上下文（Bounded Context）先划**
  - 一个上下文一个模型，同名概念在不同上下文中可以是不同模型
  - 禁止"全公司一个大模型"：概念在不同上下文语义不同（如"商品"在销售与库存上下文中含义不同）
  - 上下文边界应尽量与团队边界、部署单元边界对齐

- **通用语言（Ubiquitous Language）**
  - 类名、方法名、字段名使用业务术语，不使用技术术语
  - 术语变更时同步更新代码、文档、沟通口径
  - 禁止中英混杂命名同一概念；禁止用 `data`、`info`、`manager`、
    `helper`、`util` 这类无业务含义的词

- **上下文映射（Context Mapping）**
  - 明确上下文间关系：共享内核、客户-供应商、防腐层、开放主机服务
  - 跨上下文集成**必须经防腐层（ACL）**，禁止直接复用对方模型
  - 上下游关系要有明确的方向与契约

## 2. 战术设计（Tactical design）

### 聚合（Aggregate）

- **聚合根保证不变量**
  - 所有对聚合内部状态的修改必须经过聚合根的公开方法
  - 不变量在**构造时**与**每次状态变更时**都必须成立
  - 禁止对外暴露内部实体的可变引用（见 `coding/java/java.md` 不可变性）

- **聚合边界按不变量划，不按表划**
  - 一次事务只改一个聚合
  - 需要原子修改的数据放同一聚合；不需要的不要凑在一起
  - 禁止为每张表建一个聚合；禁止把整个对象图做成一个大聚合

- **聚合间只通过 ID 引用**
  - 禁止聚合 A 持有聚合 B 的对象引用（会破坏边界、造成加载级联）
  - 跨聚合一致性用领域事件 + 事务性 outbox，**不做跨聚合事务**

- **聚合要小**
  - 聚合越大，锁竞争与并发冲突越严重
  - 判断标准：能否在单机内存中完整加载并在一事务内提交

### 实体（Entity）

- 有**身份标识**，标识在生命周期内不变
- `equals` / `hashCode` 基于标识，而非全部字段
- 状态可变，但变更须通过表达业务意图的方法（见下"行为暴露"）

### 值对象（Value Object）

- **无标识，由值定义**：两个值对象属性相同即为相等
- **必须不可变**：创建后不可修改，变更即产生新对象
- **必须实现 `equals` / `hashCode`**（优先用 record 承载）
- 用于替代"基本类型 + 校验散落各处"的场景
  ```java
  // 错误：金额校验散落在各处，可传负数、可混用币种
  void pay(BigDecimal amount, String currency)

  // 正确：约束封装在值对象内
  void pay(Money amount)
  ```
- **优先用值对象表达概念**：金额、时间区间、邮箱、手机号、坐标等

### 领域服务（Domain Service）

- 用于**不属于任何单一实体/值对象**的业务规则
- 必须是无状态的
- **不要滥用**：能放到聚合里的逻辑不要抽成领域服务
- 命名体现业务动作，不叫 `XxxManager` / `XxxHelper`

### 领域事件（Domain Event）

- 表示**已经发生的**业务事实，命名用过去式（`OrderCreated`、`PaymentFailed`）
- 事件是不可变的，只承载必要数据（含标识，不含大对象图）
- 领域事件用于跨聚合/跨上下文的最终一致性，**不用于替代同步调用**
- 发布须与状态变更原子（同一事务写 outbox），不能先提交再发消息

### 工厂（Factory）

- 复杂聚合的创建逻辑封装在工厂方法中，优先于公开构造器
- 构造器私有 + 静态工厂方法，保证创建出的对象一定满足不变量

## 3. 领域层纯净性（Purity）

- **领域层不依赖框架**
  - 不出现 Spring、MyBatis、JPA、Jackson、Web 相关注解或类型
  - 不需要容器即可实例化与测试
- **领域层不依赖基础设施**
  - 不直接访问数据库、消息队列、HTTP、文件系统
  - 需要外部资源时定义端口（Port）接口，由基础设施实现
- **领域层无技术概念**：不出现 `DTO`、`Entity`（ORM 意义）、`VO`（视图意义）、
  `Controller`、`Request`、`Response` 等词
- **允许的依赖**：JDK 标准库、极少数无框架侵入的工具库
- **领域逻辑可纯单测**：领域测试不启动 Spring 容器（见
  `coding/spring/spring-boot.md` 测试策略）

## 4. 仓储与端口（Repository & Ports）

- **仓储接口定义在领域侧**
  - 接口语义是**领域集合**（如"订单集合"），不是数据访问对象
  - 方法命名体现领域意图：`findPendingOrders()` 而非 `selectByStatus()`
  - 禁止在接口中暴露 ORM 特有类型（`EntityManager`、`Criteria`、`Session`）
- **实现在基础设施侧**
  - 基础设施实现仓储接口，负责 ORM 映射、连接、缓存
  - 领域对象与持久化对象（PO/DO）**必须分离**，禁止穿透到上层
- **仓储与 DAO 的区别**
  - 仓储：面向聚合，一个聚合一个仓储，表达领域集合
  - DAO/Mapper：面向表，可多个表对应一个 DAO，属于基础设施内部实现细节
- **仓储不返回半成品**：返回完整可用的聚合，不返回需要再次加载的对象
- **查询与命令分离（简化 CQRS）**
  - 写路径必须经聚合
  - 纯查询场景允许绕过领域层直查（只读、无业务规则），
    **禁止用于写路径**，且不得返回领域对象供上层修改

## 5. 一致性（Consistency）

- **一个聚合一个事务**：事务边界在应用服务层
- **跨聚合最终一致性**：领域事件 + 事务性 outbox（至少一次投递 +
  下游幂等），详细机制参见 outbox 模式说明
- **不引入分布式事务**：不为聚合间协作使用 XA / 两阶段提交
- **接受最终一致**：向业务方明确说明延迟窗口与补偿策略
- **幂等是前提**：所有事件消费者必须幂等（按消息标识去重）

## 6. 模型与数据库（Model vs Schema）

- **领域模型不是表结构映射**
  - 允许模型与表结构不一致：值对象可内联到主表、聚合可跨多表
  - 禁止"表有什么字段，模型就有什么字段"的机械映射
- **ORM 映射放在基础设施**，通过映射器/转换器完成双向转换
- **禁止把 ORM 实体直接当领域模型**（懒加载代理、无参构造、字段可变
  会污染领域层）
- **表结构变更不自动等于模型变更**：加字段可能只是基础设施细节

## 7. 审查清单（Review checklist）

设计或评审领域模型时逐项确认：

- [ ] 限界上下文边界明确，无跨上下文直接复用模型
- [ ] 代码术语与业务术语一致，无技术化命名
- [ ] 每个聚合有明确的不变量清单，且在变更时被校验
- [ ] 聚合边界按不变量划分，非按表划分
- [ ] 聚合间只通过 ID 引用，无对象引用
- [ ] 一次事务只修改一个聚合
- [ ] 值对象不可变且实现了 `equals` / `hashCode`
- [ ] 实体相等性基于标识而非全部字段
- [ ] 聚合创建有工厂方法，不变量在构造时保证
- [ ] 领域层无框架依赖，可脱离容器单测
- [ ] 领域层无技术概念命名（DTO / VO / Request 等）
- [ ] 仓储接口在领域侧，实现不在领域层
- [ ] 领域对象与持久化对象已分离，无穿透
- [ ] 领域事件用过去式命名，与状态变更原子发布
- [ ] 跨聚合一致性走事件 + outbox，未使用跨聚合事务
- [ ] 事件消费者已实现幂等

## 8. 禁止事项（Prohibited）

- 用技术术语命名业务概念（`XxxManager`、`XxxHelper`、`data`、`info`）
- 贫血模型：领域对象只有 getter/setter，逻辑全在 Service
- 突破聚合根直接修改内部实体
- 聚合间持有对象引用（应为 ID）
- 一次事务修改多个聚合
- 为每张表建一个聚合
- 值对象可变或未实现 `equals` / `hashCode`
- 领域层引入 Spring / ORM / Web / 序列化框架依赖
- 在领域层出现 DTO / VO / Request / Response 等分层概念
- 仓储接口暴露 ORM 特有类型
- 领域对象与持久化对象互相穿透
- 先提交事务再发领域事件（应同事务写 outbox）
- 跨聚合使用分布式事务
- 事件消费者无幂等处理
- 用领域事件替代同步调用（需要即时结果的场景）
