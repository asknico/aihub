# AI Code Generation Rules

> 适用范围：AI Agent 生成新代码时的行为约束。  
> 边界：修改既有代码见 `code-modification.md`；Agent 通用行为见 `agent-behavior.md`；安全与敏感操作见 `safety.md`；工具使用见 `tool-usage.md`。  
> 上位约束：`common/general.md` 的所有规则在本文件之上，冲突时以其为准。

## 0. 核心原则（Core principle）

1. **不猜测，先确认**：读代码与配置后再生成，禁止基于命名或直觉假设。
2. **生成不是目的，可运行才是**：未编译、未测试的产出不算完成。
3. **复用优先于新建**：新建文件是最后手段，不是第一反应。
4. **最小可用**：不生成"以后可能需要"的代码。
5. **诚实的产出**：未验证的内容必须标注，不把"应该可以"表述为"已完成"。

## 1. 生成前（Before generating）

### 1.1 上下文获取

- **读规则文件**：先读 `AGENTS.md` 及项目内适用的规则文件，确认约束边界。
- **理解项目结构**：确认模块划分、包结构、分层方式，产物必须落在既有结构内。
- **识别既有约定**：命名风格、错误处理方式、日志方式、测试框架与风格、依赖管理方式必须与既有代码一致。
- **确认技术栈版本**：框架与语言版本决定可用语法与 API，禁止使用项目基线之外的特性。

### 1.2 调研与复用

- **先搜索再生成**：确认是否已存在同类组件、工具类、基类、已有实现（用全仓库检索，不只看当前目录）。
- **优先复用**：能复用则复用，能扩展则扩展，都不行才新建。
- **禁止重复造轮子**：出现功能高度重合的新类即为缺陷。
- **确定影响范围**：列出将被创建、修改、间接影响的模块与文件，并检查是否存在共享代码、公共契约或跨模块依赖。

### 1.3 前置确认（须先询问，不得自行决定）

- 涉及数据库结构变更
- 涉及对外 API 或消息契约变更
- 涉及鉴权、加密、密钥、权限模型
- 涉及跨服务 / 跨仓库接口
- 需要引入新依赖（须按 `common/general.md` §4 给出理由）
- 需求存在多种合理实现路径且取舍影响较大
- 规则文件与用户指令存在冲突

> 不确定时，宁可提问。一次确认的成本远低于一次错误生成。

## 2. 生成中（When generating）

### 2.1 架构合规

- **遵循项目架构**：产物必须符合既定分层与依赖方向（参见 `architecture/dependency-rules.md`）。
- **不跨越领域边界**：不把 A 上下文的逻辑写进 B 上下文；跨上下文集成经防腐层（参见 `architecture/ddd.md`）。
- **不破坏层级依赖**：高层不直接使用低层实现细节；跨层经接口。

### 2.2 抽象克制

- **不引入不必要的抽象**
  - 不为单次使用创建接口、工厂、策略类
  - 不生成空的扩展点、占位实现、预留配置项
  - 抽象需有当前即存在的 2 个以上使用方（参见 `common/general.md` §2）
- **不生成企业级样板**：除非项目既有风格如此，不额外添加Builder、Visitor、多层继承等结构。

### 2.3 代码质量

- **符合语言层规则**：Java 代码遵循 `coding/java/java.md`，Spring 代码遵循 `coding/spring/spring-boot.md`。
- **不产出半成品**：不生成 TODO 占位、写死的临时值、注释掉的实现、未接线的分支。
- **不引入冗余**：不生成无用的 import、未使用的方法、重复的校验逻辑。
- **异常与日志**：遵循 `common/general.md` §7 / §8，不静默吞异常，不在循环内打日志，不打印敏感信息。
- **注释说明意图**：解释"为什么"而非"做什么"；不复述代码已表达的内容。

### 2.4 测试

- **同步生成测试**：新增行为必须附带测试；缺陷修复必须附带能复现该缺陷的测试。
- **测试层级正确**：领域逻辑用纯单测；Web 层用切片测试；不为简单逻辑启动完整容器（参见 `coding/spring/spring-boot.md` §7）。
- **测试必须可运行**：不生成无法执行的测试骨架，不依赖执行顺序。
- **不生成空断言**：测试必须有明确断言，禁止只调用不校验。

### 2.5 文档

- **架构变更时更新文档**：模块划分、接口契约、配置项变化须同步更新。
- **新增配置项须更新示例配置**。
- **不为代码生成冗余说明文件**：不创建与既有文档重复的 README。
- **接口文档与实现同步**：不留下过期的注释或文档。

## 3. 生成后（After generating）

### 3.1 验证（必须实际执行）

- **编译项目**：产出必须能编译通过，无新增告警。
- **运行相关测试**：执行受影响范围的测试，确认通过。
  - 测试失败时**修复问题**，不得跳过、禁用或删除失败用例
- **检查格式与静态分析**：符合项目格式化与静态检查要求。
- **改动范围复核**：逐个确认被修改文件都是必要的，还原无关变更。

> 未实际运行即宣称"已通过"属于严重违规。
> 无法运行时必须说明原因与未验证的部分。

### 3.2 合规检查

- **检查架构违规**：确认未越层、未跨边界、未引入循环依赖。
- **检查规则冲突**：确认产出未违反 `common/general.md` 及领域规则。
- **检查兼容性**：确认未破坏对外接口、数据库结构、消息格式。

### 3.3 汇报

汇报内容须包含：

1. **做了什么**：变更的文件清单与各自作用
2. **为什么这样做**：关键设计选择与理由
3. **如何验证**：执行的命令与实际结果
4. **未解决的问题**：编译错误、失败测试、待确认事项
5. **风险与假设**：必须假设的地方、潜在影响范围
6. **建议的后续动作**：需要人工决策或补充的部分

禁止行为：

- 隐瞒失败结果或淡化问题严重性
- 用"应该可以""理论上没问题"代替实际验证
- 只报告成功部分，不报告未完成部分
- 把未验证内容表述为已完成

## 4. 产出质量门禁（Quality gates）

生成任务完成前须全部满足：

- [ ] 编译通过，无新增告警
- [ ] 相关测试通过，无跳过或禁用
- [ ] 新增行为有对应测试
- [ ] 产物落在既有目录结构与命名约定内
- [ ] 无跨层调用、无越界依赖
- [ ] 未新增不必要抽象、占位实现或 TODO
- [ ] 未修改与任务无关的文件
- [ ] 未引入未经确认的新依赖
- [ ] 无密钥、凭据、真实数据入库
- [ ] 配置变更已同步示例配置
- [ ] 架构变更已同步文档
- [ ] 已实际执行验证并如实汇报结果

## 5. 禁止事项（Prohibited）

- 未读代码即生成，基于假设产出实现
- 生成与既有组件功能重复的新实现
- 生成空实现、占位方法、未接线分支
- 生成 TODO / FIXME 代替实现
- 为单次使用引入接口、工厂、策略等抽象层
- 使用项目基线之外的语法或依赖
- 破坏既有分层或跨越领域边界
- 生成后不编译、不测试
- 跳过或禁用失败测试以让构建通过
- 未实际运行即宣称验证通过
- 隐瞒失败结果或未完成部分
- 把未验证内容表述为已完成
- 手工修改生成文件（应改生成源，参见 `common/general.md` §3）
