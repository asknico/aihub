# 通用工程规则（General Engineering Rules）

> 适用范围：所有项目、所有模块、所有 Agent。
> 定位：最高优先级的基础约束，与领域规则冲突时以本文件为准。
> 原则：规则必须可判定、可验证、可争论。含糊的规则等于没有规则。

## 0. 核心原则（Core principle）

1. **最小充分改动**（Minimal Sufficient Change）
   解决当前问题所需的最小改动量。不为"以后可能需要"提前设计，不为"顺便优化"扩大范围。

2. **先理解，后动手**
   在读完相关代码、确认调用方、明确数据流之前，不产生任何修改。禁止基于猜测改代码。

3. **显式优于隐式**
   不依赖框架的隐式行为、不依赖字段顺序、不依赖"默认配置正好是我要的"。所有关键假设必须写在代码或注释里。

4. **可回滚**
   每次改动都应能独立回滚。禁止把"重构"与"功能变更"混在同一次提交里。

5. **不做无授权的重构**
   发现设计问题时，先记录并在回复中提出，不擅自重构与当前任务无关的代码。

## 1. 修改既有代码（Modifying existing code）

- **先理解再修改**：动手前必须完成
  - 定位所有调用方（`rg` 全仓库检索，不只看当前文件）
  - 确认是否有测试覆盖；无覆盖时先补最小测试或明确告知风险
  - 确认该接口是否对外开放（跨服务 / 跨团队 / 已发布 SDK）
  - 确认是否涉及数据库、消息、缓存等有状态依赖

- **最小改动优先**
  - 优先修改现有结构，而不是新增抽象层
  - 禁止"顺手"重命名、调整格式、重排 import
  - 格式化差异应与逻辑改动分离提交

- **不改无关文件**
  - 提交前逐一确认每个被修改文件的必要性
  - 因工具自动格式化产生的无关变更，必须还原

- **向后兼容**
  - 默认保持兼容：公开 API 签名、数据库结构、消息格式、配置文件键名
  - 不兼容变更须显式声明，并给出迁移方案（含回滚步骤）
  - 兼容性优先级：对外接口 > 跨服务契约 > 模块间接口 > 模块内结构
  - 破坏性变更处理路径：新增 → 双写/双读 → 切流 → 下线旧路径

- **修改前必须确认的场景**（须先询问，不得自行决定）
  - 涉及数据库结构变更
  - 涉及对外 API 或消息契约变更
  - 涉及鉴权、加密、密钥、权限模型
  - 跨仓库 / 跨服务的接口调整
  - 影响线上行为的性能相关改动

## 2. 抽象与设计（Abstraction）

- **三次原则**：同一段逻辑出现第三次时才考虑抽取。第二次出现时容忍重复。
- **禁止预防性抽象**：不为"将来可能扩展"预留接口、配置项、策略模式。
- **抽象必须有读者**：新增的接口、基类、泛型参数，必须能指出当前就有 2 个以上实现或调用方。
- **依赖方向单向**：高层不依赖低层实现细节；跨层调用须经明确定义的接口。
- **边界清晰**：模块对外暴露的入口越少越好。默认 private，必要时才放开可见性。
- **无循环依赖**：出现循环依赖时，说明边界划分有问题，应调整边界而非绕过。

## 3. 文件与产物（Files & artifacts）

- **不手工修改生成物**：代码生成器、编译产物、锁文件、构建输出目录。
  需要变更时，改生成源或生成配置，然后重新生成。
- **不提交密钥**：密钥、令牌、证书、连接串、个人凭据一律不入版本库。
  使用环境变量或密钥管理服务；示例文件只留占位符（`.env.example`）。
- **不创建冗余文件**：
  - 禁止为临时验证创建长期存在的文件
  - 禁止创建内容与现有文档重复的说明文件
  - 禁止提交编辑器配置、本地缓存、调试残留
- **文件命名与位置遵循既有约定**：新文件放入现有目录结构，不新建平行目录。
- **删除优于注释**：无用的代码直接删除（版本控制可找回），不保留注释掉的代码块。

## 4. 依赖管理（Dependencies）

- **优先使用现有依赖**：引入新依赖前，先确认现有库能否满足需求。
- **新增依赖必须说明**（在提交信息或回复中给出）
  - 解决什么具体问题
  - 为什么现有依赖无法满足
  - 维护状态：最近发布、活跃度、是否有安全记录
  - 体积与传递依赖影响
  - 引入成本：学习曲线、配置复杂度
- **禁止的依赖行为**
  - 为单个小功能引入重量级框架
  - 引入与现有依赖功能重叠的库（同类库只保留一个）
  - 引入无人维护、无版本发布、来源不明的库
  - 使用 SNAPSHOT / 非稳定版本作为生产依赖
- **版本管理**：统一在父 POM / BOM 中集中管理版本号，子模块不重复声明版本。
- **依赖变更后必须验证**：完整构建 + 依赖冲突检查（`mvn dependency:tree`）。

## 5. 质量门禁（Quality gates）

改动提交前须全部满足：

- **可构建**：完整编译通过，无新增警告。
- **可测试**：现有测试全部通过，无跳过、无注释禁用。
- **有覆盖**：新增逻辑有对应测试；缺陷修复必须附带能复现该缺陷的测试。
- **可解释**：能说明"为什么这样改"和"为什么不用别的方案"。
- **可观测**：涉及关键路径的改动，补充必要的日志、指标或埋点（不引入噪声日志）。
- **无隐患**：无遗留 TODO 替代实现、无写死的临时值、无调试代码。

## 6. 提交与评审（Commits & review）

- **原子提交**：一次提交只做一件事。重构与功能变更分开。
- **提交信息说明意图**：讲清"为什么"，而非复述"改了什么"（差异本身已说明后者）。
- **单一职责的变更集**：单个 PR 的改动范围应能用一句话概括。
- **可评审性**：单次改动过大时应拆分；无法拆分时须说明理由。
- **自审先行**：提交前自行完整过一遍 diff，检查有无遗漏、误改、残留调试代码。

## 7. 错误处理（Error handling）

- **不静默吞异常**：捕获后必须有处理动作（记录、转换、补偿、上抛），禁止空 catch 块。
- **不捕获过宽的异常**：避免 `catch (Exception)` 兜底全部；只捕获能实际处理的类型。
- **失败要显式**：宁可快速失败并暴露问题，也不要返回"看起来正常"的错误结果。
- **区分可恢复与不可恢复**：可恢复错误做有界重试（含退避与上限），不可恢复错误快速上抛。
- **错误信息可诊断**：包含上下文（标识、参数、原因），但不泄露敏感信息。

## 8. 日志与可观测性（Logging）

- **日志分级恰当**：ERROR 需人介入，WARN 需关注，INFO 记录关键状态流转，DEBUG 用于排查。
- **不打印敏感信息**：密码、令牌、完整身份证/银行卡号、个人隐私字段须脱敏。
- **不在循环内打日志**：批量场景用聚合统计或采样，避免日志洪泛。
- **结构化优先**：关键业务日志采用结构化字段，便于检索与告警。

## 9. 安全底线（Security）

- **输入不可信**：所有外部输入（请求、消息、文件、配置）均需校验，包括内部服务间调用。
- **最小权限**：数据库账号、服务账号、令牌权限按需授予，不图省事用超级权限。
- **参数化查询**：禁止拼接 SQL；ORM 与原生 SQL 均须使用参数绑定。
- **输出编码**：防止注入与 XSS，禁止直接拼接用户输入到日志、SQL、命令、模板。
- **依赖漏洞**：新增或升级依赖后执行漏洞扫描，高危问题必须处理或明确豁免理由。

## 10. 禁止事项清单（Prohibited）

以下行为一律禁止，除非用户明确要求：

- 修改与本任务无关的文件
- 手工编辑生成文件或锁文件
- 将密钥、凭据、真实数据写入代码或版本库
- 注释掉代码代替删除
- 用 TODO / FIXME 代替实现
- 在测试中跳过或禁用失败的用例来"通过"构建
- 为让代码编译通过而引入不必要依赖
- 在无测试覆盖的关键路径上做未经确认的改动
- 擅自变更数据库结构或对外契约
- 提交包含调试输出、临时硬编码值的代码

## 11. 不确定时（When uncertain）

- **优先提问**，不猜测后大批量改动。
- **给出选项**：列出可行方案、各自代价与建议，而非只抛问题。
- **标注假设**：必须假设时，在回复中显式写明，便于纠正。
- **暴露风险**：发现潜在问题时主动指出，即使不在当前任务范围内。
- **不假装完成**：未验证的部分明确说明"未验证"，不模糊表述为"已完成"。
